This guide walks a service team through migrating from the legacy job scheduler to the new workflow engine. The migration is designed to be incremental: both systems can run side by side for as long as needed, and each job can be moved independently, so there is no big-bang cutover and no maintenance window required. Before starting, confirm three prerequisites. Your service must be on runtime version 4.2 or later, because earlier runtimes lack the workflow client library. Your job definitions must live in the declarative config format, not the deprecated inline annotations; if you still use annotations, run the converter tool first and commit its output. Finally, your team needs a workflow namespace, which the platform team provisions within one business day of a request ticket. The migration itself proceeds in four stages per job. Stage one is shadowing: register the job in the workflow engine with the execution flag set to dry-run. In this mode the engine schedules the job on its normal cadence and records what it would have executed, but performs no side effects. Compare the shadow log against the legacy scheduler's execution history for at least one full scheduling cycle; for weekly jobs this means waiting a week, and teams are explicitly discouraged from shortcutting the comparison window because most divergences the platform team has debugged were timezone and daylight-saving edge cases that only appear at cycle boundaries. Stage two is takeover: flip the execution flag to live and simultaneously disable the job in the legacy scheduler. The order matters, and the tooling enforces it: disabling the legacy job first would create a gap where nothing runs, while enabling live mode first would double-execute. The migration CLI performs both operations in a single transaction against the control plane, and it refuses to proceed if the shadow comparison from stage one shows any unexplained divergence. Stage three is verification: for two scheduling cycles after takeover, the engine tags the job's runs with a migration marker, and the observability dashboard shows a dedicated panel comparing run duration, exit status, and output volume against the historical baseline imported from the legacy scheduler. Regressions beyond twenty percent on any metric page the owning team automatically, not the platform team, a deliberate choice so that ownership of job health transfers on day one rather than lingering with the migration tooling. Stage four is cleanup: delete the job's definition from the legacy scheduler's config repository. This is the only irreversible step, and the CLI requires an explicit confirmation naming the job. The legacy scheduler retains execution history for ninety days after deletion, exported nightly to the archive bucket, after which the job's legacy record is gone entirely. Two categories of job need special handling. Jobs with downstream dependencies declared in the legacy scheduler's dependency graph cannot use the standard CLI flow, because the workflow engine models dependencies as explicit workflow edges rather than scheduler-level ordering hints; these jobs must be migrated as a dependency-closed group, and the grouping tool computes the closure for you from the legacy graph. Second, jobs that write to the shared reporting database need their credentials rotated during takeover, because the workflow engine injects credentials from the vault rather than reading them from the scheduler's environment, and the old environment-scoped credentials are revoked as part of stage two for these jobs specifically. Expect the whole process to take about two weeks of calendar time per service for typical portfolios of ten to twenty jobs, dominated by the mandatory shadow and verification windows rather than by hands-on work, which totals a few hours.
