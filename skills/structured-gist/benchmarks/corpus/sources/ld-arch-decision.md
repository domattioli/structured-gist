This document records the decision to store user-generated document attachments in object storage with metadata in the relational database, rather than storing the attachment bytes in the database itself or adopting a dedicated document store. The context: the collaboration product is adding file attachments to comments. Product requirements call for attachments up to 100 megabytes, permanent retention unless a user deletes them, region-pinned storage for regulated tenants, and download latency under two seconds at the 95th percentile for files up to 10 megabytes. Current scale projections estimate 40 terabytes of attachment data in the first year, growing roughly linearly with the existing comment volume, which itself grows about 8 percent quarter over quarter. Three options were evaluated. Option A stored attachment bytes directly in the relational database as large binary columns. Its appeal is transactional consistency: an attachment and its comment row commit or roll back together, and backup tooling covers everything uniformly. It was rejected because the projected data volume would multiply the database's storage footprint by roughly fifteen times, degrading backup and restore times that are already the tightest constraint in the disaster-recovery budget, and because large binary reads through the database connection pool would compete with transactional queries for the same capacity. Option B adopted a dedicated document database for both attachment bytes and attachment metadata. It was rejected on operational grounds: it introduces a third storage system to run, monitor, back up, and secure, while providing no capability the combination of object storage and the existing relational database lacks for this workload. The team also noted that no current engineer has production experience operating the candidate system, which converts every incident into a learning exercise. Option C, the selected design, writes attachment bytes to the object store under a key derived from the tenant, the attachment identifier, and a content hash, while a metadata row in the relational database records the key, size, content type, upload state, and the owning comment. Consistency between the two systems is handled with a two-phase upload: the client first requests an upload slot, which creates a metadata row in the pending state and returns a signed upload URL; after the client completes the upload, a confirmation call transitions the row to active. A nightly reconciliation job deletes orphaned objects whose metadata row is still pending after 24 hours, and flags metadata rows whose object is missing, which indicates a bug rather than an expected state. Region pinning falls out of the object store's per-bucket region configuration: each regulated tenant maps to a bucket in its required region, and the metadata row carries the bucket name, so the serving path needs no region logic beyond reading the row. Download latency is met by issuing short-lived signed URLs so that bytes flow directly from the object store to the client without transiting the application servers; a load test with synthetic 10-megabyte files measured 1.4 seconds at the 95th percentile from the slowest supported region. Two consequences of this decision are accepted rather than solved. Deleting a tenant now requires coordinating deletion across two systems, and the compliance team's deletion-verification report must join object-store inventory against database metadata rather than querying one system. And point-in-time restore of the database after an incident can resurrect metadata rows whose objects were legitimately deleted in the interim; the reconciliation job's missing-object flag is the designated detection mechanism for this case, and the restore runbook now includes running it immediately after any restore.
