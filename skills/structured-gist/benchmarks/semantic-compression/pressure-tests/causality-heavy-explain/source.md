The team moved the webhook receiver from synchronous processing to a queue-based async model, and the reason only makes sense as a chain, not as a list of separate facts.

It started with the receiver's synchronous design: whenever a webhook arrived, the handler called a downstream enrichment API directly and held the HTTP request open until that call returned. That downstream API was already slow under normal conditions, often taking several seconds to respond. Because the handler waited on it synchronously, a slow downstream call meant the webhook sender's HTTP connection stayed open for that same several seconds. Under any real load, some of those calls ran long enough to exceed the sender's timeout, so the sender started seeing timeouts on a meaningful fraction of requests. Senders that see a timeout assume the request failed and, by design, retry it — so every timeout produced a retry, and the retry was itself a new synchronous call to the same already-slow endpoint. That meant retries didn't relieve pressure on the downstream API, they added to it, which pushed more calls past the timeout threshold and produced still more retries. During ordinary traffic this loop stayed small enough to go unnoticed, but during peak traffic the same feedback loop ran hot enough to cascade: the downstream API's queue depth grew faster than it could drain, latency climbed further, timeout rates climbed further, and retry volume climbed further, until the receiver was spending most of its capacity on retried requests instead of new ones.

That cascade is what drove the decision to introduce a message queue in front of the enrichment step. With the queue in place, the webhook receiver acknowledges the sender immediately on receipt and hands the enrichment work to a worker process instead of doing it inline. Because the receiver's response time no longer depends on the enrichment API's response time, the two are decoupled — the receiver's latency and the downstream API's latency stopped being coupled to each other. With that coupling gone, a slow downstream call no longer produces a sender-facing timeout, which means it no longer produces a retry, which means the specific retry-storm failure mode that caused the cascades is gone, not just less frequent.
