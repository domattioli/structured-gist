- **v0.3.9** (2026-07-24, operator-directed, follow-on to v0.3.8 same session): **responsive goes glyph-free.** Operator screenshot minutes after v0.3.8 shipped: the Claude Code app renders each `responsive` list item with its own bullet, so the v0.3.7-mandated ladder glyph inside the content produced `• ▸ What you saw` / `• ↪ my recap…` — two markers on one line, the exact defect R10 bans at the source layer, reproduced by the spec itself at the render layer. - **v0.3.8** (2026-07-24, operator-directed, GitHub-rendering defect): **GitHub prose routed to `responsive`; `inline` deprecated.** Operator: nested-notes bodies on issue/PR comments render as "a mess" — indents off, `↪`/enumerator lines in unreasonably-wide horizontal-scroll code blocks, `▸` lines starting with an emoji outside any code block. Root cause (confirmed against raw bodies + CommonMark): `inline` mode indents each rung 4 spaces under a real `- ` list item, and GFM treats a line indented ≥4 spaces past a list item's content column as an **indented code block** — so depth-2+ rungs (`↪`/`a.` at 8 spaces) became non-wrapping code boxes and depth-1 `▸` lines (4 spaces) became emoji-led paragraphs. The v0.3.7 `responsive` mode (real GFM nested list, `- ▸ …`, 2-space/rung) already renders correctly on *any* variable-width markdown surface — GitHub included — but v0.3.7 wrongly scoped it to chat apps and left GitHub on the broken `inline`. Fix is spec/guidance-only (no linter or example-fixture change — the linter already validates `responsive` and keeps `inline` back-compat detection for pre-v0.3.8 committed outlines): mode table collapsed to two active modes (`block`, `responsive`) + `inline` marked DEPRECATED with the GFM-code-block reason; Activation surface-keyed default now sends *any* markdown surface (GitHub + chat) → `responsive`; description, Spacing blank-line note, Emphasis-taxonomy scope, worked-example parenthetical all repointed inline→responsive. Companion (outside this skill): DomI `CLAUDE.md` communication-style table GitHub row and `comment-issue reference/github-authoring.md` repointed `inline`→`responsive`. pytest 33/33 + linter 7/7 unchanged (no rule logic touched).
- **v0.3.7** (2026-07-22, operator-directed, follow-on to v0.3.6, option b of a/b/c): **new render mode `responsive`, for chat-app surfaces.** v0.3.6's R11 hard-wrap (64-char width, identical-indent continuations) fixed phone soft-wrap for MONOSPACE surfaces, but under-fills desktop chat viewports (operator: "the box is less wide"). Root insight: only the renderer knows the box width, so chat surfaces should delegate wrapping to the renderer via REAL markdown list nesting instead of the linter guessing a width. `responsive`: each node is a genuine GFM unordered list item whose content starts with the ladder glyph (`- ▸ Purpose`), nested via real list indentation (2 spaces/rung, GFM-standard); enumerators are literal content (`- I. assemble context` — real ordered-list syntax would renumber); `↪` leaves as `- ↪ ...`; no fence. The renderer wraps every line to its actual box width with a hanging indent — full-width on desktop, clean on phone, no source-side hard-wrap. Mode table now three rows: `block` (fenced, monospace/terminal + committed `.md` fences; R11 applies), `inline` (GitHub prose, unchanged), `responsive` (chat-app; **new default there** — Activation default is now surface-keyed: chat → `responsive`, terminal/plain → `block`).
